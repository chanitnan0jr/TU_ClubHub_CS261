## 1. Description

**As a:** นักศึกษาที่ผ่านการคัดเลือกเข้าชมรมและกำลังรอยืนยันสิทธิ์  
**I want to:** เลือกยืนยันสิทธิ์เพื่อเข้าร่วมชมรม หรือสละสิทธิ์ ภายในเวลาที่กำหนด  
**So that:** ฉันสามารถตัดสินใจเข้าร่วมชมรม และได้รับการขึ้นทะเบียนสมาชิกอย่างถูกต้อง

## 2. Pre-conditions

- Login ด้วยบัญชีเจ้าของใบสมัครที่ Active; การยืนยันใหม่ต้องมีนักศึกษาและชมรม Active เพิ่ม ส่วนการสละไม่บังคับ student/club Active ตาม Permission Matrix; exact Retry ผลตัดสินเดิมใช้ BR-04 ไม่ใช่การยืนยันใหม่
- สำหรับการตัดสินใหม่ ใบสมัครต้องผ่านการคัดเลือกและประกาศผลแล้ว ยังไม่ตอบรับ และอยู่ในช่วงเวลายืนยันสิทธิ์; exact Retry ของผลสำเร็จเดิมใช้ BR-04 ไม่ใช่ Transition ใหม่
- กรณีหมดเวลาเป็นเส้นทางอัตโนมัติของระบบ ไม่ต้องมีผู้ใช้ Login เพื่อกระตุ้น

## 3. Post-conditions

- ยืนยันสำเร็จ: ใบสมัครเป็น 'ยืนยันสิทธิ์' และมีสมาชิกชมรม (ClubMember) ที่เชื่อมกับนักศึกษาและชมรมถูกต้องโดยไม่สร้างซ้ำ
- สละสิทธิ์: ใบสมัครเป็น 'สละสิทธิ์' และไม่เพิ่มสมาชิกจากใบสมัครนี้
- หมดเวลาโดยไม่ตอบรับ: เปลี่ยนเป็น 'สละสิทธิ์ (หมดเวลาตอบรับ)' อัตโนมัติและไม่สร้างสมาชิก
- บันทึกเวลา/เหตุผล/ผู้ดำเนินการหรือ System Action ตามนโยบายประวัติที่ตกลง

## 4. Acceptance Criteria

- **AC-01:** ผู้ผ่านการคัดเลือกสามารถกดยืนยันสิทธิ์หรือสละสิทธิ์ได้ภายในช่วงเวลาที่กำหนดของรอบนั้นๆ
- **AC-02:** เมื่อกดยืนยันสิทธิ์ ใบสมัครจะเปลี่ยนเป็น 'ยืนยันสิทธิ์' และระบบจะขึ้นทะเบียนนักศึกษาเข้าสู่สมาชิกชมรม (ClubMember) โดยไม่สร้างข้อมูลซ้ำ
- **AC-03:** เมื่อกดสละสิทธิ์ ใบสมัครจะเปลี่ยนเป็น 'สละสิทธิ์' และไม่เพิ่มชื่อเข้าสู่ทะเบียนสมาชิก
- **AC-04:** หากพ้นกำหนดเวลาตอบรับแล้วผู้สมัครยังไม่ดำเนินการ ระบบต้องปรับสถานะเป็น 'สละสิทธิ์ (หมดเวลาตอบรับ)' อัตโนมัติ
- **AC-05:** ระบบต้องป้องกัน Concurrency และการกดยืนยันซ้ำหลายครั้ง โดยให้มีผลลัพธ์การขึ้นทะเบียนสมาชิกเพียงครั้งเดียว

## 5. Scope

### อยู่ในขอบเขต

- ตรวจสิทธิ์และเงื่อนไขตอบรับที่ Backend
- ยืนยัน/สละสิทธิ์และบันทึกสมาชิก/สถานะอย่างสอดคล้อง
- เปลี่ยนสถานะอัตโนมัติเมื่อหมดเวลาตาม AC-04
- จัดการคำขอซ้ำ คำขอพร้อมกัน และการแสดงผลใน US-04

### ไม่รวมใน Story นี้

- การพิจารณาและประกาศผลคัดเลือก
- ระบบแก้ไขทะเบียนสมาชิกทั่วไป การลาออก หรือยกเลิกสมาชิกหลังยืนยัน
- การเปลี่ยนใจหลังตอบรับ: T74-D05 ตัดออกจาก MVP แล้ว คำขอสวนทางหลังจบรายการปฏิเสธ 409 โดยไม่แก้ข้อมูลเดิม
- โควตาสมาชิกใหม่หรือจำนวนสูงสุดที่ไม่มีข้อกำหนดยืนยัน

## 6. Business Rules

กฎด้านล่างขยายความ AC เพื่อให้พัฒนาและทดสอบได้ตรงกัน ส่วนเรื่องที่ AC ยังไม่ระบุแยกไว้ในหัวข้อ 10

| รหัส | กฎ | อ้างอิง |
|---|---|---|
| BR-01 | สำหรับการตัดสินใหม่ Backend ตรวจเจ้าของบัญชี Active, ACCEPTED ที่ยังไม่ตอบรับ, รอบไม่ cancelled และการประกาศจริง; ยืนยันต้อง student/club Active ส่วนสละไม่บังคับสองเงื่อนไขนั้น ตรวจเวลาใน Transaction ไม่อาศัยปุ่ม Frontend; Retry ผลเดิมใช้ BR-04 | AC-01 |
| BR-02 | การตัดสินใหม่ใช้ `results_published_at <= now < confirmation_deadline` โดย sample เวลา Server ณ จุดตัดสินใน Transaction หลังได้สิทธิ์เขียน ไม่ใช้เวลาเปิดฟอร์มหรือเวลาเครื่องผู้ใช้; ตรง deadline ปฏิเสธการตัดสินใหม่ตาม T74-D06 | AC-01, AC-04; T74-D06 |

### ผลลัพธ์ของการตอบรับ

| เงื่อนไขก่อนทำรายการ | เหตุการณ์ | ผลลัพธ์ที่ผู้ใช้เห็น | ผลต่อสมาชิก |
|---|---|---|---|
| ผ่าน ประกาศแล้ว ยังไม่ตอบรับ และอยู่ในช่วงเวลา | ยืนยันสำเร็จ | ยืนยันสิทธิ์ | มีสมาชิกถูกต้องโดยไม่สร้างซ้ำ |
| ผ่าน ประกาศแล้ว ยังไม่ตอบรับ และอยู่ในช่วงเวลา | สละสำเร็จ | สละสิทธิ์ | ไม่สร้างสมาชิกจากใบสมัครนี้ |
| ผ่าน ประกาศแล้ว ยังไม่ตอบรับ และพ้นกำหนด | ระบบหมดเวลาอัตโนมัติ | สละสิทธิ์ (หมดเวลาตอบรับ) | ไม่สร้างสมาชิก |
| CONFIRMED หรือ DECLINED แล้ว | exact Retry Action เดิมของใบสมัครเดิม | คืนผลตัดสินเดิม ไม่ใช่การตัดสินใหม่ | ไม่มี writes ไม่สร้าง/คืนสถานะสมาชิก แม้สมาชิกปัจจุบันเปลี่ยนไป |
| ACCEPTED และมีแถวสมาชิกเดิมของคู่คน/ชมรมไม่ว่าสถานะใด | ยืนยันใหม่ | ปฏิเสธ 409 RESOURCE_CONFLICT | รักษาสมาชิก ประวัติ และ source เดิม ไม่ reactivate |
| CONFIRMED/DECLINED แล้ว หรือหมดเวลา | คำขอสวนทาง/ตอบรับใหม่หลังจบ | ปฏิเสธ 409 ไม่มีเปลี่ยนใจใน MVP | ไม่แก้สมาชิกหรือสถานะสุดท้าย |

ข้อความในตารางเป็นข้อความ UI; [Schema ปัจจุบัน](../../../backend/src/main/resources/db/migration/V1__init_schema.sql) มี `CONFIRMED`, `DECLINED`, `EXPIRED` แยกกันแล้ว ไม่ใช้ `DECLINED` แทนการหมดเวลาและไม่สร้างตารางใหม่จากชื่อ Domain Object

## 7. Main Flow

1. นักศึกษาเปิดใบสมัครที่ผ่านและประกาศผลจาก US-04
2. ระบบแสดงกำหนดเวลาและตัวเลือกเมื่อยังมีสิทธิ์ตอบรับ
3. ผู้ใช้เลือกยืนยันหรือสละสิทธิ์และยืนยันการตัดสินใจ
4. Backend ตรวจเงื่อนไขปัจจุบันและทำรายการอย่างปลอดภัยต่อคำขอพร้อมกัน
5. ระบบแสดงผลล่าสุด; การยืนยันใหม่ที่สำเร็จสร้างสมาชิก เส้นทางสละไม่สร้างสมาชิก ส่วน exact Retry คืนผลตัดสินเดิมของใบสมัครโดยไม่แก้สมาชิกปัจจุบัน ไม่แสดงว่าการ Retry เป็นการ reactivate
6. หากไม่มีการตอบรับจนหมดเวลา ระบบเปลี่ยนสถานะอัตโนมัติและ US-04 แสดงผลหมดเวลา

## 9. Quality Criteria และ Constraints

- **ความถูกต้อง:** ข้อมูลและสถานะที่แสดงต้องตรงผลธุรกิจที่จัดเก็บและเงื่อนไขที่อนุญาตให้เปิดเผย
- **ความปลอดภัย:** ตรวจสิทธิ์ที่ Backend ทุก Endpoint ที่เกี่ยวข้อง ไม่ใช้เพียง Route Guard หรือการซ่อนปุ่มบน Frontend
- **ความชัดเจนของหน้าจอ:** แยก Loading, Empty, Error และผลสำเร็จ ผู้ใช้ต้องไม่เข้าใจว่าทำรายการสำเร็จเมื่อ Backend ปฏิเสธ
- **ข้อมูลขั้นต่ำ:** Response ส่งเฉพาะข้อมูลที่จำเป็น ห้ามมีรหัสผ่าน TU, Application-Key หรือข้อมูล Session ลับ
- **ความสอดคล้อง:** Frontend, Backend, QA ใช้ State/Permission/Error Contract เดียวกัน หาก AC นี้ขัด Matrix เดิมให้ยืนยันและปรับเอกสารร่วมกันก่อนเปลี่ยน Implementation
- **การทดสอบ:** ใช้ข้อมูลจำลองที่ตรวจผลได้และ Mock TU ใน CI; ไม่พึ่งบัญชี TU จริงในการทดสอบอัตโนมัติ
- **ข้อกำหนดร่วม:** ใช้ NFR และกฎ Repository ที่ทีมกำหนด ไม่ตั้ง Response Time, Coverage หรือจำนวนโควตาใหม่จากเอกสารนี้

ตารางนี้แยกข้อสรุปที่บันทึกจากคำสั่งผู้ใช้ออกจากรายละเอียด Design ที่ยังเปิด ข้อสรุปมีสถานะ Decision recorded / Pending Team Review ไม่ใช่ formal PO sign-off หรือผล Review ของ FE/BE/QA แล้ว

|---|---|
| ชื่อสถานะในฐานข้อมูล | หลักฐาน SQL/Architecture ปัจจุบันมี `CONFIRMED` / `DECLINED` / `EXPIRED` แล้ว: สละเองใช้ `DECLINED`, หมดเวลาใช้ `EXPIRED` และ UI แสดง 'สละสิทธิ์ (หมดเวลาตอบรับ)'; กรณีหมดเวลา `responded_at` เป็น NULL และ history ใช้ actor ระบบตามแบบเดิม ไม่ใช่การเพิ่มสถานะใหม่ |
| ช่วงเวลาที่ใช้ | **T74-D06 — Decision recorded / Pending Team Review:** การตัดสินใหม่ใช้ `results_published_at <= now < confirmation_deadline` ณ จุดตัดสินใน Transaction หลังได้สิทธิ์เขียน โดย sample เวลา Server ขณะนั้น ไม่ใช้ `results_scheduled_at` หรือเวลาเปิดฟอร์ม |
| งานหมดเวลา | **T74-D06 — ข้อสรุปบางส่วนบันทึกแล้ว:** ต้องเปลี่ยนเป็น EXPIRED อัตโนมัติแม้ไม่มีผู้เปิดหน้าและไม่ทับผลตอบรับสำเร็จ; scheduled sweep/catch-up เป็นแนวทาง Design ความถี่/ระยะหน่วงยังเปิดให้ PO/Reviewer ตัดสิน ไม่ตั้งตัวเลขเอง |
| คำขอซ้ำและคำขอสวนทาง | **T74-D05 — Decision recorded / Pending Team Review:** Retry Action เดิมคืนผลเดิมโดยไม่สร้างสมาชิก/history ซ้ำ; คำขอสวนทางหลังจบรายการ 409 และไม่มีเปลี่ยนใจใน MVP; payload/HTTP รายละเอียดของการคืนผลเดิมอยู่ขั้น Design ไม่เปิดนโยบายธุรกิจนี้เป็นคำถามเดิมอีก |
| สมาชิกที่มีอยู่แล้ว | **T74-D07 — Decision recorded / Pending Team Review:** ผู้ใช้ยืนยันให้ปฏิเสธการยืนยันใหม่ทุกกรณีที่มีแถวสมาชิกเดิม ACTIVE/INACTIVE/LEFT/REMOVED ของคู่คน/ชมรม ด้วย 409 และไม่แก้ข้อมูลเดิม ไม่มี MVP reactivation; exact Retry ใบสมัครเดิมคืนผลเดิมโดยไม่เขียนข้อมูลแม้สมาชิกปัจจุบันเปลี่ยนสถานะ; รักษา history/source เดิมและ unique `(club_id,user_id)` |
| เส้นตายกับ Transaction | **T74-D06 — Decision recorded / Pending Team Review:** ใช้เวลา Server ณ จุดตัดสินใน Transaction หลังได้สิทธิ์เขียนเป็นจุดตรวจ ไม่ใช้เวลาที่เริ่มคำขอหรือเปิดฟอร์ม; Design ต้องระบุ lock/clock sampling และใช้ Test เดียวกันกับ expiry รวมการยืนยันข้ามชมรมที่ตรวจเพดานซ้ำ |

## 12. Definition of Done

- [ ] ทีมยืนยันประเด็นในหัวข้อ 10 ที่จำเป็นต่อการ Implement และอัปเดต Contract แล้ว
- [ ] AC-01 ถึง AC-05 ผ่านพร้อมหลักฐานแต่ละข้อ
- [ ] ทดสอบสิทธิ์ผ่าน API โดยตรง รวมกรณีผู้ใช้/ชมรม/Role ไม่ตรงเงื่อนไข
- [ ] Tests ของกฎธุรกิจและกรณีผิดพลาดสำคัญผ่าน; Integration Tests ใช้ PostgreSQL เมื่อจำเป็นต่อพฤติกรรมฐานข้อมูล
- [ ] Frontend และ Backend ทำงานร่วมกันบน Environment ทดสอบที่ระบุ และแสดงผลตรงกัน
- [ ] Build, Type Check และ Automated Tests ที่เกี่ยวข้องผ่าน CI
- [ ] ผ่าน Code Review แก้ข้อเสนอแนะที่ขัดเกณฑ์ตรวจรับ และรวมโค้ดตามกติกาทีม
- [ ] Test Report ระบุ Commit/Environment ผลแต่ละกรณี และข้อจำกัดที่ยังค้างตามจริง
- [ ] ไม่มีปัญหาคงค้างที่ทำให้ Flow หลักใช้งานไม่ได้ ข้อมูลผิด หรือเข้าถึงข้อมูลโดยไม่มีสิทธิ์
- [ ] งานหมดเวลาอัตโนมัติทำงานได้โดยไม่ต้องมีผู้เปิดหน้า และผ่าน Test คำขอพร้อมกัน/Retry/ตามเก็บหลัง Downtime

## 13. Dependencies และข้อสังเกต

US-04 แสดงผล; ต้องมีข้อมูลผลที่ประกาศจริงจาก Flow คัดเลือกแยกต่างหาก ผู้ใช้ยืนยัน [สอง Draft Stories งานบันทึก/ประกาศผล](selection-results-draft.md) และ Scope Owner ชนิตว์นันท์ — PO/SA แล้ว โดย FE/BE รอมอบหมายและ formal Team Review/Approval ยัง Pending ตาม T74-D03; Task69–70 ต้องรวม AC-04 และ Test งานหมดเวลาใน Estimate ไม่ถือว่ามีเพราะทำปุ่มยืนยันแล้ว

AC-04 และข้อสรุปผู้ใช้ T74-D06 กำหนดหมดเวลาอัตโนมัติเป็น `EXPIRED` แยกจาก `DECLINED` ไม่ใช่เพียงข้อความบน UI; ความถี่/ระยะหน่วงงานยังเปิด ส่วน Implementation และ FE/BE/QA Review ยังไม่มีหลักฐานครบ การปิด Story ต้องมีหลักฐานตาม DoD จริง

การอ้าง Task เป็นการเชื่อมกับแผนงานในบทสนทนา ไม่ใช่การยืนยันว่าโค้ดปัจจุบัน Implement ครบแล้ว
