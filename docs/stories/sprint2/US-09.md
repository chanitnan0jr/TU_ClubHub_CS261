## 1. Description

**As a:** กรรมการชมรมที่ได้รับสิทธิ์ตรวจสอบใบสมัคร  
**I want to:** เลือกรอบรับสมัคร ดูรายชื่อผู้สมัคร เปิดอ่านคำตอบ และเปิดดูลิงก์พอร์ตโฟลิโอ  
**So that:** ฉันสามารถตรวจสอบข้อมูลประกอบการสมัครอย่างเป็นระบบก่อนพิจารณาคัดเลือก

## 2. Pre-conditions

- Login สำเร็จและมีสิทธิ์กรรมการในการอ่านใบสมัครของชมรม/รอบเป้าหมายตาม Matrix
- มีรอบรับสมัครของชมรมตนเอง; เส้นทางหลักมีใบสมัครอยู่ในรอบนั้น
- หากรอบไม่มีใบสมัคร ให้แสดงรายการว่างอย่างเหมาะสม ไม่บังคับให้ต้องมีใบสมัครก่อนเปิดหน้ารายการ

## 3. Post-conditions

- กรรมการเปิดอ่านข้อมูล คำตอบ และลิงก์เอกสารได้ตามสิทธิ์
- ข้อมูลของคนละรอบ/ชมรมไม่ปะปน
- สถานะใบสมัครและการประกาศผลไม่เปลี่ยนจากการเปิดอ่าน

## 4. Acceptance Criteria

- **AC-01:** กรรมการชมรมสามารถเลือกรอบรับสมัคร และดูรายชื่อผู้สมัครทั้งหมดของชมรมตนเองได้
- **AC-02:** กรรมการสามารถเปิดอ่านรายละเอียดข้อมูลผู้สมัคร เหตุผล คำตอบคัดเลือก และเปิดลิงก์เอกสาร/พอร์ตโฟลิโอได้
- **AC-03:** คำถามและคำตอบของผู้สมัครต้องจับคู่แสดงผลถูกต้องตรงตามลำดับของรอบรับสมัครนั้น
- **AC-04:** การเปิดอ่านใบสมัครต้องไม่ทำให้สถานะใบสมัครเปลี่ยน หรือเกิดการประกาศผลโดยอัตโนมัติ
- **AC-05:** นักศึกษาทั่วไป หรือกรรมการต่างชมรม ไม่สามารถเข้าถึงหรือเปิดอ่านใบสมัครได้ (Backend ตรวจสอบสิทธิ์ 403 Forbidden)

## 5. Scope

### อยู่ในขอบเขต

- เลือกรอบและดูรายชื่อผู้สมัครในขอบเขตชมรมที่มีสิทธิ์
- อ่านรายละเอียด เหตุผล คำถาม/คำตอบ และลิงก์เอกสาร
- ตรวจสิทธิ์อ่านรายการและรายละเอียดที่ Backend
- Empty/Loading/Error และการเปิดลิงก์ภายนอก

### ไม่รวมใน Story นี้

- บันทึกผลรับ/ไม่รับ เปลี่ยนสถานะเป็น UNDER_REVIEW หรือ INTERVIEW
- ประกาศผลคัดเลือกหรือแก้หมายเหตุภายใน
- อัปโหลด จัดเก็บ หรือดาวน์โหลดเอกสารแทนผู้ใช้ผ่าน Backend
- เพิ่มการนัดสัมภาษณ์ คะแนนคัดเลือก หรือ Export รายชื่อโดยไม่มี AC รองรับ

## 6. Business Rules

กฎด้านล่างขยายความ AC เพื่อให้พัฒนาและทดสอบได้ตรงกัน ส่วนเรื่องที่ AC ยังไม่ระบุแยกไว้ในหัวข้อ 10

|---|---|---|

| BR-08 | หากคำถามไม่บังคับตอบไม่มีคำตอบ ให้แสดงว่าไม่ได้ตอบ ไม่เลื่อนคำตอบข้อถัดไปมาจับคู่ผิดข้อ | AC-03 |

## 7. Main Flow

1. กรรมการ Login และเลือกชมรมที่มีสิทธิ์
2. เลือกรอบรับสมัคร
3. Backend ตรวจสิทธิ์และแสดงรายการผู้สมัครของรอบนั้น
4. กรรมการเลือกใบสมัคร
5. ระบบแสดงข้อมูลผู้สมัคร เหตุผล และคำถามคู่คำตอบตามลำดับ
6. กรรมการเปิดลิงก์เอกสารจากเว็บไซต์ต้นทางหรือกลับไปอ่านรายการอื่น โดยสถานะไม่เปลี่ยน

## 8. ข้อมูลที่เกี่ยวข้อง

| Domain Object | ข้อมูลที่ใช้ |
|---|---|
| Club / Recruitment Round | เจ้าของชมรม รอบ และชื่อรอบ |
| Committee Assignment | สิทธิ์ ตำแหน่ง วาระ และสถานะตาม Matrix |
| Application / Student | ตัวระบุใบสมัคร ข้อมูลผู้สมัครที่จำเป็น เหตุผล เวลาส่ง |
| Application Question / Answer | รหัสคำถาม ลำดับ คำตอบและรอบที่เกี่ยวข้อง |
| Application Link | ชื่อเอกสาร/คำอธิบายและ HTTPS URL |

ชื่อ Domain Object ไม่ได้กำหนดว่าต้องมีตารางหนึ่งต่อหนึ่ง ให้ใช้ Schema จริงและออกแบบ Migration เฉพาะเมื่อจำเป็น

## 9. Quality Criteria และ Constraints

- **ความถูกต้อง:** ข้อมูลและสถานะที่แสดงต้องตรงผลธุรกิจที่จัดเก็บและเงื่อนไขที่อนุญาตให้เปิดเผย
- **ความปลอดภัย:** ตรวจสิทธิ์ที่ Backend ทุก Endpoint ที่เกี่ยวข้อง ไม่ใช้เพียง Route Guard หรือการซ่อนปุ่มบน Frontend
- **ความชัดเจนของหน้าจอ:** แยก Loading, Empty, Error และผลสำเร็จ ผู้ใช้ต้องไม่เข้าใจว่าทำรายการสำเร็จเมื่อ Backend ปฏิเสธ
- **ข้อมูลขั้นต่ำ:** Response ส่งเฉพาะข้อมูลที่จำเป็น ห้ามมีรหัสผ่าน TU, Application-Key หรือข้อมูล Session ลับ
- **ความสอดคล้อง:** Frontend, Backend, QA ใช้ State/Permission/Error Contract เดียวกัน หาก AC นี้ขัด Matrix เดิมให้ยืนยันและปรับเอกสารร่วมกันก่อนเปลี่ยน Implementation
- **การทดสอบ:** ใช้ข้อมูลจำลองที่ตรวจผลได้และ Mock TU ใน CI; ไม่พึ่งบัญชี TU จริงในการทดสอบอัตโนมัติ
- **ข้อกำหนดร่วม:** ใช้ NFR และกฎ Repository ที่ทีมกำหนด ไม่ตั้ง Response Time, Coverage หรือจำนวนโควตาใหม่จากเอกสารนี้

## 10. ประเด็นที่ต้องยืนยันก่อนพัฒนา

ตารางนี้แยกข้อสรุปที่บันทึกจากคำสั่งผู้ใช้ออกจากรายละเอียด Design ที่ยังเปิด ข้อสรุปมีสถานะ Decision recorded / Pending Team Review ไม่ใช่ formal PO sign-off หรือผล Review ของ FE/BE/QA แล้ว

| ประเด็น | แนวทางหรือข้อสรุปที่ต้องมี |
|---|---|
| รายการข้อมูลผู้สมัคร | กำหนดเฉพาะข้อมูลที่จำเป็นตาม Spec ไม่ส่ง Credential/ข้อมูลบัญชีส่วนเกิน |
| ลำดับรายการ/แบ่งหน้า | กำหนดลำดับและ Pagination ใน Design หากมี ต้องเปิดดูผู้สมัครครบได้ |
| self-review | ใช้นโยบาย Matrix §4: มีใบสมัครในรอบนั้นสถานะใดก็ตาม รวม WITHDRAWN ให้ปฏิเสธทุกงานกรรมการของรอบ; กรองรอบที่ถูกห้ามก่อน pagination/count ไม่ใช่ซ่อนเฉพาะใบสมัครตนเอง |
| ทรัพยากรไม่มีอยู่/ไม่มีสิทธิ์ | T74-D01 บันทึกข้อสรุปจากผู้ใช้แล้ว: มี private resource จริงแต่ไม่มีสิทธิ์ใช้ 403; ไม่พบจริงใช้ 404; ลำดับตรวจ Session/account/CSRF คงตาม Contract และยังต้อง Review วิธีตรวจสิทธิ์ parent/child |
| เอกสารภายนอก | ผู้สมัครรับผิดชอบสิทธิ์เอกสาร ระบบแสดงลิงก์ที่บันทึกไว้ ไม่มีการตรวจปลายทางอัตโนมัติ |
