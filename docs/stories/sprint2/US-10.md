## 1. Description

**As a:** เจ้าหน้าที่ฝ่ายกิจการนักศึกษาหรือองค์การนักศึกษา (Admin)  
**I want to:** ดูภาพรวมสถานะการรับสมัคร จำนวนผู้สมัคร และจำนวนสมาชิกยืนยันสิทธิ์ พร้อมค้นหาและกรอง  
**So that:** ฉันสามารถติดตามสถานการณ์ของชมรม และนำข้อมูลไปประกอบรายงานและวางแผนสนับสนุน

## 2. Pre-conditions

- Login ด้วยบัญชีที่มีสิทธิ์ Admin / Student Affairs ของระบบ
- ข้อมูลชมรม รอบรับสมัคร ใบสมัคร และสมาชิกที่มีอยู่พร้อมให้อ่าน; กรณียังไม่มีข้อมูลสถิติให้แสดงศูนย์/รายการว่างตามความจริง

## 3. Post-conditions

- แสดงสถานะรับสมัคร จำนวนผู้สมัคร และสมาชิกจริงของทุกชมรมในขอบเขตที่กรอง
- คำค้น หมวดหมู่ ปีการศึกษา และภาคการศึกษาที่ใช้อยู่ตรงกับข้อมูลสถิติที่แสดง
- ไม่แก้ข้อมูลรอบ ใบสมัคร หรือทะเบียนสมาชิก

## 4. Acceptance Criteria

- **AC-01:** ผู้ใช้ที่มีสิทธิ์ Admin / Student Affairs สามารถเข้าดูแดชบอร์ดภาพรวมสถิติของทุกชมรมในระบบได้
- **AC-02:** แดชบอร์ดแสดงสถานะการเปิดรับสมัคร จำนวนผู้สมัคร และจำนวนสมาชิกที่ยืนยันสิทธิ์แล้ว ตรงตามข้อมูลจริง
- **AC-03:** สามารถค้นหาชมรมตามชื่อ และกรองข้อมูลตามหมวดหมู่ ปีการศึกษา และภาคการศึกษาได้
- **AC-04:** การนับจำนวนสมาชิกต้องคำนวณเฉพาะผู้ที่ยืนยันสิทธิ์แล้วเท่านั้น โดยไม่นับรวมผู้ที่ยังรอพิจารณาหรือสละสิทธิ์
- **AC-05:** ผู้ใช้ทั่วไปหรือกรรมการชมรมที่ไม่ได้รับสิทธิ์ส่วนกลาง จะถูกปฏิเสธการเข้าถึงหน้าแดชบอร์ดและ API ส่วนกลาง

## 5. Scope

### อยู่ในขอบเขต

- Dashboard ส่วนกลางของทุกชมรมตามสิทธิ์
- สถานะเปิดรับ จำนวนผู้สมัคร และจำนวนสมาชิกที่ยืนยันแล้ว
- ค้นหาชื่อชมรม กรองหมวดหมู่ ปีการศึกษา และภาคการศึกษา
- ตรวจสิทธิ์หน้าเว็บ/API และแสดง Loading/Empty/Error

### ไม่รวมใน Story นี้

- Export PDF/Excel หรือการสร้างเอกสารรายงานอัตโนมัติ
- กราฟขั้นสูง การพยากรณ์ หรือ KPI ที่ไม่ได้กำหนด
- การอ่านรายชื่อ/ข้อมูลส่วนบุคคลของผู้สมัครผ่าน Dashboard โดยไม่มีสิทธิ์เฉพาะรองรับ
- การแต่งตั้งกรรมการ แก้ผลคัดเลือก หรือจัดการสมาชิก

## 7. Main Flow

1. Admin Login และเปิด Dashboard ส่วนกลาง
2. Backend ตรวจสิทธิ์ปัจจุบันและอ่านข้อมูลสรุปตามค่าเริ่มต้น
3. แสดงชมรม สถานะรับสมัคร จำนวนผู้สมัคร และสมาชิกยืนยันแล้ว
4. ผู้ใช้ค้นหาชื่อและเลือกหมวดหมู่ ปีการศึกษา หรือภาคการศึกษา
5. ระบบคำนวณ/แสดงผลตามนิยามและเงื่อนไขเดียวกัน
6. ผู้ใช้เปลี่ยนหรือล้างเงื่อนไขและนำข้อมูลไปใช้ประกอบการรายงาน

## 8. ข้อมูลที่เกี่ยวข้อง

| Domain Object | ข้อมูลที่ใช้ |
|---|---|
| User / System Role | สิทธิ์ส่วนกลางที่ได้รับมอบหมายจริง |
| Club / Category | ชื่อชมรม หมวดหมู่ และขอบเขตชมรมทั้งหมด |
| Recruitment Round | สถานะ เวลาเปิด/ปิด ปิดจริง และการอ้างอิงปี/ภาคที่ยืนยัน |
| Application | นักศึกษา รอบ และสถานะสำหรับนับผู้สมัคร |
| Club Membership / Confirmation | หลักฐานการยืนยันและสมาชิกที่จัดเก็บสำเร็จ |

ชื่อ Domain Object ไม่ได้กำหนดว่าต้องมีตารางหนึ่งต่อหนึ่ง ให้ใช้ Schema จริงและออกแบบ Migration เฉพาะเมื่อจำเป็น

## 9. Quality Criteria และ Constraints

- **ความถูกต้อง:** ข้อมูลและสถานะที่แสดงต้องตรงผลธุรกิจที่จัดเก็บและเงื่อนไขที่อนุญาตให้เปิดเผย
- **ความปลอดภัย:** ตรวจสิทธิ์ที่ Backend ทุก Endpoint ที่เกี่ยวข้อง ไม่ใช้เพียง Route Guard หรือการซ่อนปุ่มบน Frontend
- **ความชัดเจนของหน้าจอ:** แยก Loading, Empty, Error และผลสำเร็จ ผู้ใช้ต้องไม่เข้าใจว่าทำรายการสำเร็จเมื่อ Backend ปฏิเสธ
- **ข้อมูลขั้นต่ำ:** Response ส่งเฉพาะข้อมูลที่จำเป็น ห้ามมีรหัสผ่าน TU, Application-Key หรือข้อมูล Session ลับ
- **ความสอดคล้อง:** Frontend, Backend, QA ใช้ State/Permission/Error Contract เดียวกัน หาก AC นี้ขัด Matrix เดิมให้ยืนยันและปรับเอกสารร่วมกันก่อนเปลี่ยน Implementation
- **การทดสอบ:** ใช้ข้อมูลจำลองที่ตรวจผลได้และ Mock TU ใน CI; ไม่พึ่งบัญชี TU จริงในการทดสอบอัตโนมัติ
- **ข้อกำหนดร่วม:** ใช้ NFR และกฎ Repository ที่ทีมกำหนด ไม่ตั้ง Response Time, Coverage หรือจำนวนโควตาใหม่จากเอกสารนี้

## 10. ประเด็นที่ต้องยืนยันก่อนพัฒนา

รายการต่อไปนี้เป็นคำถาม/ข้อเสนอด้าน Design ไม่ใช่ข้อกำหนดที่อนุมัติเพิ่มแล้ว

| ประเด็น | แนวทางหรือข้อสรุปที่ต้องมี |
|---|---|
| จำนวนผู้สมัครหมายถึงอะไร | เสนอจำนวนคนไม่ซ้ำต่อชมรมภายในรอบที่เข้าเงื่อนไข; ถ้าจะนับใบสมัครให้ใช้ชื่อ 'จำนวนใบสมัคร' แยก ห้ามสลับหน่วยโดยไม่ระบุ |
| ยอดรวมทุกชมรม | ผลรวมรายชมรมอาจนับคนเดียวหลายครั้ง ต้องแยกจากจำนวนผู้สมัครไม่ซ้ำทั้งระบบถ้าจะแสดงทั้งสองค่า |
| สมาชิกจริงตามปี/ภาค | เลือกว่าจะนับผู้ยืนยันจากรอบในปี/ภาคนั้น หรือสมาชิก Active ณ ช่วงเวลา; นิยามต้องสอดคล้องกับข้อมูลที่มีและแสดงชื่อ Metric ชัด |
| สมาชิกสิ้นสุดแล้ว | กำหนดว่าจะนับในสถิติการยืนยันย้อนหลังหรือไม่ และแยกจากจำนวนสมาชิก Active ปัจจุบัน |
| แหล่งข้อมูลปีการศึกษา/ภาค | [SQL ปัจจุบัน](../../../backend/src/main/resources/db/migration/V1__init_schema.sql) มี `recruitment_rounds.academic_year` และ `semester` แล้ว; T74-D08 ยังต้องตกลงว่าตัวกรองอ้างรอบ/กลุ่มสมาชิกอย่างไร ไม่เดาจากปฏิทินและไม่เพิ่ม Migration เพียงเพราะ Story เดิมยังไม่ได้ตรวจ Schema |
| หลายรอบในชมรมเดียว | เสนอแสดงรายละเอียดรายรอบหรือกำหนด Aggregate Status ชัด; ห้ามเลือกรอบใดรอบหนึ่งแบบไม่มีกฎ |
| บทบาท Student Affairs | Matrix ปัจจุบันให้ Dashboard แก่ global `ADMIN` ที่บัญชี Active และตรวจ role ล่าสุด; ต้องยืนยันการมอบหมายผู้ใช้งานจริง ไม่สร้าง System Role ใหม่จากชื่อ Actor หรือ TU employee |
| ค่าเริ่มต้นและการรวมตัวกรอง | ยืนยันปี/ภาคเริ่มต้น ขอบเขตทั้งหมด พฤติกรรมล้าง และใช้ AND ระหว่างเงื่อนไขหรือกฎอื่นใน Contract |
| 403 และ Session | เสนอผู้ Login แต่ไม่มีสิทธิ์ตอบ 403; ผู้ไม่ Login จัดการ Authentication ตาม Contract; AC นี้ยังไม่ได้กำหนด HTTP code ไว้โดยตรง |

## 12. Definition of Done

- [ ] ทีมยืนยันประเด็นในหัวข้อ 10 ที่จำเป็นต่อการ Implement และอัปเดต Contract แล้ว
- [ ] AC-01 ถึง AC-05 ผ่านพร้อมหลักฐานแต่ละข้อ
- [ ] ทดสอบสิทธิ์ผ่าน API โดยตรง รวมกรณีผู้ใช้/ชมรม/Role ไม่ตรงเงื่อนไข
- [ ] Tests ของกฎธุรกิจและกรณีผิดพลาดสำคัญผ่าน; Integration Tests ใช้ PostgreSQL เมื่อจำเป็นต่อพฤติกรรมฐานข้อมูล
- [ ] Frontend และ Backend ทำงานร่วมกันบน Environment ทดสอบที่ระบุ และแสดงผลตรงกัน
- [ ] Build, Type Check และ Automated Tests ที่เกี่ยวข้องผ่าน CI
- [ ] ผ่าน Code Review แก้ข้อเสนอแนะที่ขัดเกณฑ์ตรวจรับ และรวมโค้ดตามกติกาทีม
- [ ] Test Report ระบุ Commit/Environment ผลแต่ละกรณี และข้อจำกัดที่ยังค้างตามจริง
- [ ] ไม่มีปัญหาคงค้างที่ทำให้ Flow หลักใช้งานไม่ได้ ข้อมูลผิด หรือเข้าถึงข้อมูลโดยไม่มีสิทธิ์
- [ ] มีชุดข้อมูลและตัวเลขคาดหวังสำหรับตรวจหน่วยนับ ปีการศึกษา ภาคการศึกษา และการไม่นับสมาชิกซ้ำ

## 13. Dependencies และข้อสังเกต
