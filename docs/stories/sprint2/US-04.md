## 1. Description

**As a:** นักศึกษาที่เข้าสู่ระบบด้วยบัญชีของตนเอง  
**I want to:** เปิดดูรายการใบสมัครที่เคยส่ง ตรวจสอบรายละเอียด สถานะ ผลคัดเลือก และกำหนดยืนยันสิทธิ์  
**So that:** ฉันสามารถติดตามความคืบหน้าของการสมัครแต่ละชมรมได้อย่างโปร่งใส

## 2. Pre-conditions

- Login สำเร็จด้วยบัญชีตนเองที่ Active; ตาม Matrix ยังอ่านประวัติเดิมได้แม้ student profile หรือชมรมไม่ Active ไม่ใช้เงื่อนไขสมัครใหม่ปิดสิทธิ์อ่านของตน
- กรณีมีประวัติการสมัคร ระบบแสดงรายการของบัญชีนั้น; กรณีไม่มีประวัติยังเข้าหน้านี้ได้และแสดง Empty State ตาม AC-05

## 3. Post-conditions

- แสดงรายการและรายละเอียดใบสมัครเฉพาะของตนเอง พร้อมสถานะล่าสุดที่อนุญาตให้เปิดเผย
- ผลคัดเลือกและกำหนดยืนยันสิทธิ์แสดงตามการประกาศผลจริง
- การเปิดอ่านไม่แก้สถานะใบสมัครหรือสร้างสมาชิก

## 4. Acceptance Criteria

- **AC-01:** นักศึกษาเข้าสู่ระบบสามารถเปิดดูรายการใบสมัครทั้งหมดของตนเอง พร้อมชื่อชมรม รอบ วันเวลาที่ส่ง และสถานะล่าสุด
- **AC-02:** นักศึกษาเข้าถึงได้เฉพาะใบสมัครของตนเองเท่านั้น หากพยายามเปิดใบสมัครของผู้อื่น Backend ต้องปฏิเสธ (403 Forbidden)
- **AC-03:** ระบบต้องไม่เปิดเผยผลการคัดเลือก (ผ่าน/ไม่ผ่าน) หรือหมายเหตุภายในของกรรมการแก่นักศึกษาก่อนมีการประกาศผลอย่างเป็นทางการ
- **AC-04:** เมื่อมีการประกาศผลอย่างเป็นทางการแล้ว ผู้ผ่านการคัดเลือกจะเห็นสถานะ 'ผ่านและรอยืนยันสิทธิ์' พร้อมกำหนดเวลาตอบรับ ส่วนผู้ไม่ผ่านจะเห็นสถานะ 'ไม่ผ่าน' และไม่มีตัวเลือกยืนยันสิทธิ์
- **AC-05:** หากนักศึกษายังไม่เคยสมัครชมรมใดมาก่อน ระบบต้องแสดงข้อความแจ้งว่ายังไม่มีประวัติการสมัคร

## 5. Scope

### อยู่ในขอบเขต

- รายการใบสมัคร รายละเอียดและประวัติที่เปิดเผยให้นักศึกษาได้
- สถานะล่าสุด ผลคัดเลือกหลังประกาศ และกำหนดเวลายืนยันสิทธิ์
- Empty/Loading/Error และการเชื่อมต่อไปทำรายการใน US-05

### ไม่รวมใน Story นี้

- การส่ง/แก้ไข/ถอนใบสมัคร
- การพิจารณาหรือประกาศผล
- การลงมือยืนยัน/สละสิทธิ์และสร้างสมาชิก ซึ่งเป็น US-05
- การเปิดเผยหมายเหตุภายในหลังประกาศผล: ไม่มี AC อนุญาต จึงไม่เพิ่มเป็นข้อมูลแสดงผล

## 6. Business Rules

กฎด้านล่างขยายความ AC เพื่อให้พัฒนาและทดสอบได้ตรงกัน ส่วนเรื่องที่ AC ยังไม่ระบุแยกไว้ในหัวข้อ 10

| รหัส | กฎ | อ้างอิง |
|---|---|---|
| BR-01 | อ่านได้เฉพาะเจ้าของใบสมัคร โดย Backend ใช้ตัวตนจาก Session ไม่เชื่อ userId ที่ Client ส่งมา | AC-01, AC-02 |
| BR-02 | รายการต้องไม่ปนใบสมัครคนอื่น; ใบสมัคร/private resource มีอยู่แต่ผู้เรียกไม่มีสิทธิ์ให้ 403 ACCESS_DENIED; ไม่พบจริงให้ 404 RESOURCE_NOT_FOUND ตามข้อสรุปผู้ใช้ T74-D01 ไม่ใช้ 404 ซ่อนใบสมัครผู้อื่น | AC-02; T74-D01 |
| BR-03 | ก่อนประกาศ ให้แสดงสถานะสำหรับผู้สมัครที่ไม่เผยผล เช่น อยู่ระหว่างพิจารณา ตาม Mapping ที่ทีมยืนยัน ไม่ส่ง ACCEPTED/REJECTED ภายในแล้วหวังให้ Frontend ซ่อน | AC-03 |
| BR-04 | ป้องกันผลรั่วผ่านรายละเอียด ประวัติสถานะ ข้อความ เหตุผล และข้อมูลเสริม ไม่ใช่แค่ช่อง status; ไม่ส่งหมายเหตุภายในใน Response นี้ | AC-03 |
| BR-05 | แสดงผลตามการประกาศจริง ไม่ถือว่าถึงเวลาประกาศตามแผนแล้วเท่ากับประกาศเรียบร้อย | AC-03, AC-04 |
| BR-06 | เมื่อผลเผยแพร่แล้ว ใบสมัครผ่านที่ยังไม่ตอบรับและยังอยู่ในช่วงตอบรับแสดง 'ผ่านและรอยืนยันสิทธิ์' พร้อมกำหนดเวลา ผู้ไม่ผ่านแสดง 'ไม่ผ่าน' ไม่มีตัวเลือกยืนยัน | AC-04 |
| BR-07 | เมื่อยืนยัน สละ หรือหมดเวลาแล้ว ให้แสดงผลล่าสุดตาม US-05 ไม่แสดงรอยืนยันต่อไปเพียงเพราะเคย ACCEPTED | AC-01, AC-04; เชื่อม US-05 |
| BR-08 | ไม่เคยสมัครให้แสดง 'ยังไม่มีประวัติการสมัคร' โดยไม่ใช้ข้อความนี้แทน API Error | AC-05 |
| BR-09 | คำขออ่านข้อมูลไม่เปลี่ยนเป็น UNDER_REVIEW หรือสร้างเหตุการณ์ตัดสินผลโดยอัตโนมัติ | ขอบเขตการอ่านข้อมูล |

## 7. Main Flow

1. นักศึกษา Login และเปิดหน้าใบสมัครของฉัน
2. Backend ตรวจ Session และดึงเฉพาะใบสมัครของเจ้าของบัญชี
3. แสดงชื่อชมรม รอบ วันเวลาที่ส่ง และสถานะที่เปิดเผยได้
4. ผู้ใช้เลือกใบสมัครเพื่ออ่านรายละเอียดและประวัติ
5. หากประกาศผลแล้ว แสดงผลและข้อมูลตอบรับตามเงื่อนไข
6. หากผ่านและยังตอบรับได้ เชื่อมไปดำเนินการใน US-05

## 8. ข้อมูลที่เกี่ยวข้อง

| Domain Object | ข้อมูลที่ใช้ |
|---|---|
| Application | เจ้าของ รอบ เวลาส่ง สถานะปัจจุบัน |
| Club / Recruitment Round | ชื่อชมรม ชื่อรอบ เวลาประกาศจริง และกำหนดยืนยัน |
| Application Status History | เหตุการณ์/เวลาที่นักศึกษามีสิทธิ์เห็น ไม่ส่ง History ภายในทั้งหมด |
| Application Answer / Link | รายละเอียดใบสมัครของเจ้าของตาม Contract ที่กำหนด |

ชื่อ Domain Object ไม่ได้กำหนดว่าต้องมีตารางหนึ่งต่อหนึ่ง ให้ใช้ Schema จริงและออกแบบ Migration เฉพาะเมื่อจำเป็น

## 9. Quality Criteria และ Constraints

- **ความถูกต้อง:** ข้อมูลและสถานะที่แสดงต้องตรงผลธุรกิจที่จัดเก็บและเงื่อนไขที่อนุญาตให้เปิดเผย
- **ความปลอดภัย:** ตรวจสิทธิ์ที่ Backend ทุก Endpoint ที่เกี่ยวข้อง ไม่ใช้เพียง Route Guard หรือการซ่อนปุ่มบน Frontend
- **ความชัดเจนของหน้าจอ:** แยก Loading, Empty, Error และผลสำเร็จ ผู้ใช้ต้องไม่เข้าใจว่าทำรายการสำเร็จเมื่อ Backend ปฏิเสธ
- **ข้อมูลขั้นต่ำ:** Response ส่งเฉพาะข้อมูลที่จำเป็น ห้ามมีรหัสผ่าน TU, Application-Key หรือข้อมูล Session ลับ
- **ความสอดคล้อง:** Frontend, Backend, QA ใช้ State/Permission/Error Contract เดียวกัน หาก AC นี้ขัด Matrix เดิมให้ยืนยันและปรับเอกสารร่วมกันก่อนเปลี่ยน Implementation
- **การทดสอบ:** ใช้ข้อมูลจำลองที่ตรวจผลได้และ Mock TU ใน CI; ไม่พึ่งบัญชี TU จริงในการทดสอบอัตโนมัติ
- **ข้อกำหนดร่วม:** ใช้ NFR และกฎ Repository ที่ทีมกำหนด ไม่ตั้ง Response Time, Coverage หรือจำนวนโควตาใหม่จากเอกสารนี้

## 10. ประเด็นที่ต้องยืนยันก่อนพัฒนา

ตารางนี้แยกข้อสรุปที่บันทึกจากคำสั่งผู้ใช้ออกจากรายละเอียด Design ที่ยังเปิด ข้อสรุปมีสถานะ Decision recorded / Pending Team Review ไม่ใช่ formal PO sign-off หรือผล Review ของ FE/BE/QA แล้ว

| ประเด็น | แนวทางหรือข้อสรุปที่ต้องมี |
|---|---|
| สถานะภายในกับสถานะแสดงผล | T74-D04 ยังต้องกำหนด Mapping ก่อน/หลังประกาศโดยไม่เปิดเผยผล; T74-D02 ตัด INTERVIEW ออกจาก MVP และ UNDER_REVIEW optional ไม่เกิดจาก GET |
| ลำดับและ Pagination | เสนอเรียงเวลาส่งล่าสุดก่อน; ระบุขนาดหน้าใน Design ถ้ามี |
| รายละเอียดประวัติ | กำหนดเหตุการณ์ที่แสดงและตัดเหตุการณ์ภายในที่ทำให้อนุมานผลได้ |
| 404 กับ 403 | **T74-D01 — Decision recorded from user instruction / Pending Team Review:** ใช้ 403 สำหรับ private resource ที่มีอยู่แต่ไม่มีสิทธิ์ตาม AC-02/US-09 และ 404 เมื่อไม่พบจริง; ต้องสะท้อนใน API/QA ตามข้อสรุป ไม่ใช่ประเด็นเลือก 403/404 ที่ยังเปิด |
| เขตเวลา | แสดงเวลาและเขตเวลาเดียวกันกับ US-05 และรอบรับสมัคร |

- [ ] ผ่าน Code Review แก้ข้อเสนอแนะที่ขัดเกณฑ์ตรวจรับ และรวมโค้ดตามกติกาทีม
- [ ] Test Report ระบุ Commit/Environment ผลแต่ละกรณี และข้อจำกัดที่ยังค้างตามจริง
- [ ] ไม่มีปัญหาคงค้างที่ทำให้ Flow หลักใช้งานไม่ได้ ข้อมูลผิด หรือเข้าถึงข้อมูลโดยไม่มีสิทธิ์

## 13. Dependencies และข้อสังเกต

US-03 สร้างข้อมูลใบสมัคร; การประกาศผลเป็น Dependency แยกและไม่ได้ถูกเพิ่มเข้า US-09 อัตโนมัติ; US-05 อัปเดตผลตอบรับ; Task64 เป็นงานพัฒนาที่เชื่อมโยง

Pre-condition เดิมที่ว่า 'มีประวัติการสมัคร' ใช้กับเส้นทางที่มีข้อมูลเท่านั้น ไม่ใช้เป็นเงื่อนไขปิดกั้นหน้า เพราะ AC-05 ต้องรองรับผู้ที่ยังไม่มีประวัติ

การอ้าง Task เป็นการเชื่อมกับแผนงานในบทสนทนา ไม่ใช่การยืนยันว่าโค้ดปัจจุบัน Implement ครบแล้ว
